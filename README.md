1. Reference Understanding
When I analyzed the reference game, I realized that its core gameplay is more than just matching three identical objects. The main challenge comes from combining three different puzzle mechanics. First, the player has to search for the correct objects among many different items. Second, because objects are stacked and partially hidden, the player must find a way to access the desired object instead of simply selecting it. Finally, the limited tray capacity requires the player to manage available space carefully before creating matches.
While I develop my game I wanted to preserve the core gameplay experience of interacting with 3D objects, collecting them into a tray, matching three identical items, and completing level objectives under time pressure. I also kept the idea of overlapping objects, since it encourages players to think about both searching and accessibility rather than simple matching.
Instead of copying the reference game directly, I created my own theme called Explorer Match. While playing the reference, I initially assumed that the objective was simply to clear the entire board because I did not immediately notice the target list. To make the objectives clearer, I introduced mission cards at the beginning of each level. These cards explain what the player needs to collect and connect the gameplay to a small adventure story. For example, one level asks the player to gather the required materials to repair a broken bridge. After completing the objectives, the player sees a success screen showing that the bridge has been repaired before continuing the journey. I believe this approach makes the objectives more visible and gives players additional motivation beyond simply clearing objects.
2. Your Implementation
I developed a playable prototype called Explorer Match, inspired by the reference game's core gameplay while introducing my own theme and progression.
The game begins with a main menu where the player can view the current level, remaining lives, and profile information. Players can create and save their own nickname, which remains available between sessions until they choose to reset it. The settings menu allows players to enable or disable music, sound effects, and vibration, and these preferences are also saved between play sessions. Since the prototype does not include an in-game economy, I added simple buttons to refill lives and boosters for testing purposes.
Before each level starts, the player is presented with a unique mission card. Each of the ten handcrafted levels introduces a different objective connected to the Explorer Match adventure theme. Instead of simply clearing objects, the player completes small story-driven tasks such as gathering materials to repair a bridge, preparing a campsite, crossing a river, or opening an ancient gate. These mission cards explain why the player needs to collect specific items and provide context for the gameplay.
During gameplay, the player selects 3D objects directly from the board. Selected objects play a flying animation towards the tray and are represented inside the tray using corresponding 2D icons to keep the interface clean and readable. A yellow outline and selection effect provide immediate visual feedback when an object is chosen. Whenever three identical objects are collected, they are automatically grouped together, merged with a short animation, accompanied by particle and sound effects, and then removed from the tray.
The gameplay also includes three boosters: Hint, Freeze, and Undo. The Hint booster highlights matching objects on the board, the Freeze booster temporarily stops the countdown timer while displaying a screen-freezing visual effect, and the Undo booster returns the most recently collected object from the tray back to the board.
The HUD displays the current level, remaining lives, countdown timer, pause button, tray, and the goal cards showing the required collectible objects. As objectives are completed, the remaining counts decrease, and completed goal cards disappear with a small animation. The player wins when every required objective has been completed. Losing occurs either when the tray becomes full without creating a match or when the timer reaches zero. In both situations, an appropriate game over screen is shown, including confirmation before returning to the main menu in order to prevent accidental life loss.
The prototype currently contains 10 levels and nearly 50 different object prefabs. To keep the project focused on the core gameplay experience, I intentionally did not implement more advanced systems such as an in-game shop, coins, daily rewards, advertisements, or additional animation systems.
3. Architecture
The project is organized into two scenes: a Main Menu scene and a Game Scene. All gameplay takes place within the single Game Scene. Instead of creating a separate scene for each level, I implemented a data-driven level system using ScriptableObjects. Each level is represented by a LevelData asset containing the level timer, objectives, available objects, mission card information, and the images displayed after completing the level.
When a level starts, the SpawnManager reads the active LevelData and spawns the required objects inside predefined spawn areas using randomized positions and rotations. Every collectible object uses the same SelectableObject script and is identified by its own ObjectID, allowing the matching system to remain generic and reusable.
When the player selects an object, it moves to the tray while its data is transferred to the corresponding tray slot. The TrayManager continuously checks whether three objects with the same ObjectID have been collected. When a match is found, the matched objects are removed, the remaining tray items shift to the left, and the tray is checked again for additional matches.
The user interface is separated into dedicated canvases for the Main Menu and the Game Scene. Within the Game Scene, the goal panel, tray, timer, booster buttons, pause menu, and win/lose screens are all managed through a single gameplay canvas.
For persistence, I used PlayerPrefs to save essential game data, including the player's current level, remaining lives, booster counts, player name, audio settings, and vibration preferences.
Instead of relying on a single large GameManager, I separated responsibilities into specialized manager classes such as LevelManager, GoalManager, TrayManager, BoardManager, BoosterManager, PauseManager, TimerManager, AudioManager, and HapticManager. Most of these managers follow the Singleton pattern, allowing different gameplay systems to communicate efficiently while keeping the project modular and easier to maintain.
4. Problems Solved
One of the most challenging parts of the project was synchronizing the tray system, UI, and object animations. During gameplay, the player selects a 3D object from the board, while the tray displays a corresponding 2D icon instead of the original 3D model. When objects were selected very quickly, sometimes a match animation had not finished before the next object was added to the tray. This occasionally caused white placeholder images to appear, incorrect tray positioning, and animation conflicts.
To solve this, I synchronized the interaction flow between gameplay logic and UI updates. I temporarily disabled new object selections while a match animation was being processed, preventing new objects from entering the tray before the previous operation had finished. I also delayed clearing UI references until the corresponding animations were fully completed, which eliminated the white placeholder issue. In addition, I safely stopped active DOTween animations before starting new ones to prevent overlapping animation states.
5. Known Issues
The prototype focuses on the core gameplay experience, so several secondary systems were intentionally left out. If I had more development time, I would further improve the visual polish of the game by adding more refined animations and visual effects. I would also redesign the win screens with my own custom artwork for each level to better support the adventure theme. In addition, I would like to create unique lose screens for different levels to make failures feel more connected to each mission.
There are no major known gameplay bugs. However, in rare cases, some objects may spawn slightly outside the intended play area or collide with the invisible boundary objects used to prevent them from falling off the board. 
6. Next Steps
If this prototype were developed into a full mobile game, my next priority would be implementing a complete progression and monetization system. I would introduce a coin system that allows players to earn and spend currency on extra lives and boosters. Instead of using the temporary refill buttons included in the prototype, these resources would be obtained through rewarded advertisements or in-app purchases.
I would also expand the gameplay by introducing new boosters that become available as players progress through the game. Unlocking additional mechanics over time would keep the gameplay fresh while gradually increasing the game's strategic depth.
Another improvement would be expanding the adventure theme by introducing different environments. For example, the first ten levels could focus on preparing for the expedition, while later levels would take place in newly discovered locations, each with its own visual style, objectives, and atmosphere. This would create a stronger sense of progression throughout the game.
Finally, I would continue polishing the overall presentation by improving the visual effects, animations, and UI artwork.
